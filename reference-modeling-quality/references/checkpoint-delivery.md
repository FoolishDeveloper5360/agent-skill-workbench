# 可恢复检查点与交付

## 内容与版本绑定

本节的 `.blend`、重开工程和模型预览要求适用于已经开始建模的阶段。建模前的二维推断方案不要求模型文件，也不能为满足检查点要求提前建模。将原始参考（或可追溯来源）、各版本推断图、关键假设与确认记录保存在已授权项目中；尚未确认时明确标记待确认，不提前写入通过状态。

单图任务的每个模型检查点应在 `qa/` 中包含当时采用的已确认方案及确认记录，注明方案版本与模型版本的对应关系，纳入清单。仅记录一个会被替换的图路径不足以复现设计依据；保留对应图文件和假设。后续方案修订不改写旧检查点。

检查点目录使用稳定版本标识，至少包含当前可打开的 `.blend` 源工程、所需纹理/依赖、QA 记录和现有重建代码/参数；当前阶段已生成的 GLB 与预览图一起纳入。尚未导出或尚未生成预览的粗模阶段，在记录中注明缺项及原因。生成预览可以发生在保存前，但向用户发送预览必须在检查点持久保存并验证之后。

建议采用 `source/`、`textures/`、`export/`、`qa/`、`rebuild/` 分组，仅创建实际有内容的目录。手工项目写明手工步骤与所需版本，不假装可以由代码完全重建。文件名称不能代替内容验证：重新打开源工程，确认依赖能找到；纹理可打包到源文件，也可使用完整的相对路径目录。程序材质和外部资产按真实依赖处理。

保存完成后生成清单，不把会继续变化的工作文件当作冻结版本。清单内相对路径、字节数、SHA-256 用于关联源工程、导出与 QA。

重开验证不得改写冻结文件。验证后新增检查图、确认记录或 QA 结果时，须在发送预览前重新生成并验证清单；保存凭据可记在检查点外，避免验证后又修改包内文件造成清单失效。

## 工具用法

在技能目录执行，下面路径仅为示例：

    python scripts/checkpoint_manifest.py create /path/to/checkpoint
    python scripts/checkpoint_manifest.py verify /path/to/checkpoint

默认清单名为 `manifest.json`；可用 `--manifest 文件名.json` 改为其他根目录文件名。脚本不接受符号链接、Windows 重解析点（包括目录联接和部分云端占位文件）、特殊文件、空包、路径穿越或重复路径。需先将云端文件完整下载到普通本地目录。目录读取失败时停止；空目录不纳入清单。验证默认也拒绝未登记的新增文件。工具不会改动模型，只创建/覆盖指定清单（清单原有内容若有保留需求请先另存）。失败返回非零状态。

清单不能证明 `.blend` 可打开、贴图已全部收齐、GLB 正确，也不能检测一位攻击者同时篡改文件与清单。需要独立可信记录时，另记录清单本身的 SHA-256 到交付凭据；不要把清单自身加入其哈希列表形成循环。

## 持久化与验证顺序

1. 在本地冻结当前检查点，重开源文件并检查依赖，运行清单创建及验证。
2. 使用已获授权的持久保存渠道保存完整目录或归档。用户指定保留的本地项目目录可以直接作为该位置，无需重复复制到同一处，也不强制外部上传。说明保存范围，不要因为本地路径可访问就认定它永久可恢复；也不要擅自新增外部账户、共享权限或发布。
3. 检查实际保存结果，确认版本、文件大小和接收方可访问范围。能够下载回读时，下载到另一个目录，解包后再次验证清单；否则明确所用的较弱验证方式与限制。不要把仅“开始上传”说成完成。
4. 记录可用的持久标识/交付链接、验证方法和时间；只有证据支持时才说已保存并可恢复。随后发送对应版本的预览和必要说明。
5. 编辑后变为新版本，重新冻结和验证；旧检查点不能替新版本背书。保存失败则先修复或请求所需保存渠道，不能跳过而声称已有备份。

持久保存渠道由任务环境和授权决定，不依赖某一产品或连接器。交付仅使用用户可访问的文件/链接；不得暴露私人内部路径或把临时目录路径伪装为下载链接。
